{\color{ink}\LARGE From document to\\structured JSON}\par\vspace{5mm}
\textbf{The task:} extract the fields and repeated records requested by a schema from a PDF or image, while preserving what the document actually prints.

DocQuorum prepares document evidence, chooses one document route, and produces one or more separate candidate JSONs. It checks each candidate independently and, when the route uses quorum, selects the candidate with the strongest agreement with the others.

\sub{1\quad Define the extraction task}
The input is a document $D$, a schema $S$ (or a JSON template), and optionally a task description $T$. The intended output is a JSON object $Y$ whose fields, types, and repeated records follow $S$ and whose values are supported by $D$:
\[
(D,S,T)\;\longrightarrow\;Y.
\]
The schema supplies both structure and instructions. For example, it can request a purchase-order number, a supplier name, and every line item with its quantity and unit price. Descriptions can specify grouping, units, missing values, or whether a page number means the PDF index or the printed folio.

\begin{tabularx}{\linewidth}{@{}p{30mm}YY@{}}\toprule
 & Example input & Intended output\\\midrule
Document & Purchase order with a header and item table & Values grounded in those pages\\
Schema & Order number; supplier; list of items & One object with those keys and an item array\\
Optional task & ``Extract every ordered item.'' & Task text becomes the schema's top-level description\\\bottomrule
\end{tabularx}

\sub{What a ``reading'' means}
A reading produces one candidate JSON, using one model call or many smaller calls. MinerU produces source evidence: page text and HTML tables. The parse-based reader maps that evidence to the schema. Readers can share source evidence, but never receive one another's candidate JSONs.

\chapterpage{STEPS 1--2 / PREPARE AND ROUTE}{Turn the document into usable evidence}
\sub{Step 1. Normalize and inspect}
\textbf{Input:} PDF or image, schema/template, optional task.\par
\textbf{Operation:} copy a PDF into a temporary workspace, or convert an image to an RGB PDF at 150 dpi. Convert a template to a schema. If supplied, the task replaces the top-level schema description. Count pages and inspect the PDF text.

The routing test is \code{len(plain_text.strip()) >= 50 * max(1, n_pages)}. It measures aggregate text availability, not OCR accuracy. A scanned PDF with enough embedded OCR text takes the text-present route. Mixed documents are classified as a whole.

For a document below this threshold, the API probes the parser endpoint. If available, MinerU processes the pages and caches each page as \code{NNNN.txt}. Text blocks remain text; tables retain HTML cell structure. Existing cached files are reused. The document cache key is derived from its bytes.

\textbf{Output:} normalized PDF, page count, text flag, text-layer strings, optional cached parse. Page images are rendered when a reader requests them.

\sub{Step 2. Select a reader route}
\begin{tabularx}{\linewidth}{@{}p{33mm}Yp{33mm}@{}}\toprule
Priority & Condition & Decision\\\midrule
1. Column flow & At least two pages; at least three nearly equal-width columns on at least half of sampled pages & Column reader\\
2. Ruled scan & No sufficient text layer; cached tables map to schema fields with conversion ratio $\geq0.9$ & Ruled reader\\
3. General & Neither specialized condition holds & General reading route\\\bottomrule
\end{tabularx}
The column test samples up to four pages and requires column-width coefficient of variation below 0.12. Ruled mode is intended for scanned tables with printed lines between records. Its router first tests the cached table's compatibility with the schema; the reader later detects the printed lines in page images.

\sub{What ``conversion ratio'' counts}
Conversion means moving parsed table cells into records with the requested field names. For example, a table row \code{item: Pen, quantity: 5} becomes a JSON record with \code{item} and \code{quantity} fields. The router computes:
\[
\text{conversion ratio}=\frac{\text{converted records}}{\text{considered parsed table-body rows}}.
\]
If 95 records are converted from 100 considered rows, the ratio is 0.95 and passes the 0.9 threshold. Pages marked bad by the converter are excluded from this calculation. The ratio measures structural compatibility; it does not measure value accuracy or coverage of every document page.

The cache remains source evidence. The ruled reader extracts its final records from image bands, with a detected row count and the table header attached to each band.
\textbf{Data boundary:} answer keys do not enter preparation, routing, reading, checks, or candidate selection. Benchmark scoring is a separate operation after extraction.

\chapterpage{STEP 3 / GENERAL READER}{Plan, read, inspect, and reduce the scope}
\textbf{Input:} schema and PDF, with either text-layer pages or cached parse pages. The primary reader uses page images when text is insufficient. Parse mode uses cached text only if its page count covers at least 90\% of the extracted page-text count; otherwise it falls back to the text layer.

\textbf{Output:} one candidate JSON and call/plan reports. Both primary and parse-based readings use these fallback strategies: try eligible plans in order and stop at an accepted result.

\begin{tabularx}{\linewidth}{@{}p{29mm}YY@{}}\toprule
Plan & When attempted & What it does\\\midrule
1. Whole\newline document & Input estimate $\leq100{,}000$ tokens; output estimate $\leq140{,}000$; image-only input has $\leq12$ pages & \textbf{Keep everything together.} Full schema + available document evidence in one call.\\
2. Schema groups & Whole plan did not return; schema exceeds 60,000 compact characters; text exists or $n\leq12$ & \textbf{Split requested fields.} Read smaller schema groups; use page windows if needed.\\
3. Text windows & Earlier plans did not return; text exists; no top-level arrays & \textbf{Split source text.} Ask for the same fields in successive windows; merge filled values.\\
4. Scalars + lists & Earlier plans did not return & \textbf{Read scalars and lists.} Read single-value fields, then each list in page chunks.\\\bottomrule
\end{tabularx}

An invoice's number, date and supplier are scalars; its item rows form a list. The 140,000-token output estimate is a planning cutoff, not a response budget: actual whole-document replies are capped at 32,000 tokens in this baseline.

\sub{What each model call sees}
Whole calls attach up to 12 page images; parse-based scans of 13--24 pages can pair pages. Longer whole calls use text only. Partitioned long scans can use eight images per window; ordinary text windows target 60,000 tokens. OCR is labeled as machine-read alongside images.

Text chunks contain text only; image chunks attach up to two pages. Chunk size is one or two pages, based on row density and field count against a 9,000-token output target. Fields named with ``page'' force one-page chunks. Earlier chunk predictions are not fed into later calls; rows are collected in page order.

\sub{What causes a retry or fallback}
\begin{itemize}
\item A whole reply ending with \code{finish_reason=length} may be retried at 32,000 output tokens. Continued truncation triggers the next plan.
\item A guided whole reply missing schema keys is retried with all keys required; a usable retry replaces it.
\item Truncated \emph{text} chunks split recursively, up to depth four; keep the halves' result only if it has more rows. Image chunks are not recursively split by this logic.
\item A text chunk with at least five estimated rows but no extracted records gets one extra attempt with a row-count reminder.
\end{itemize}
Schema/window merging fills empty fields, keeps the first nonempty scalar and the longer list; window lists are not concatenated. Scalar extraction uses the first two pages in image mode; for text over 240,000 characters, it uses the first three and last two pages.

\chapterpage{STEP 3 / ALTERNATIVE READERS}{Read the geometry that defines a record}
\sub{Column reader: preserve the reading order}
\textbf{Input:} page images from a document routed as column flow, and the schema's main array.\par
\textbf{Operation:}
\begin{enumerate}
\item Render each page at 300 dpi and crop its detected columns.
\item Read each crop from top to bottom with the item schema. The decoding schema requires the item fields and permits a null lead field.
\item Collect records in page order, then column order. Assign the physical PDF page index to \code{source_page}.
\item If a record has an empty lead field and a preceding record exists, treat it as a continuation: fill empty fields in the previous record and append string content.
\end{enumerate}
\textbf{Output:} one candidate object containing the main array. The lead field is the first required string field whose name does not contain ``page'', with a fallback to the first property. A mistaken empty lead field can therefore cause an incorrect join.

\sub{Ruled reader: use printed lines to count records}
\textbf{Input:} a routed scanned table and the schema's main array.\par
\textbf{Operation:}
\begin{enumerate}
\item Render the page at 200 dpi, deskew it, and detect horizontal rules.
\item Identify a header and row bands of up to 12 rows.
\item Stack the header above each band so every call sees the column labels.
\item Decode an array with \code{minItems = maxItems = n}, where $n$ is the detected row count for that band.
\item Attach the physical page index and concatenate records in page order.
\end{enumerate}
\textbf{Output:} one main-array candidate, then the layout check chain. A page with no detected row bands yields no records from this reader. The row constraint relies on correct rule detection; it does not establish that the values are correct.

\sub{One-shot reader: an additional candidate for short scans}
The general API attempts the ExtractBench \code{VLLMExtractProvider} reader for documents without sufficient text and with at most 12 pages. It uses that provider's prompt and rendering configuration (150 dpi) with the configured extraction model. Its JSON receives the one-shot check chain.

This is a separate reading strategy. It does not revise the primary reader's JSON. If this call raises an exception, the API logs the failure and continues with available candidates.

\sub{Why these readers are separate}
A column crop makes small print readable and preserves column order. A ruled band provides a physical count of rows. The one-shot strategy provides another interpretation of the same short scan. Specialized layout output is returned directly after checks; it does not compete in the general quorum.

\chapterpage{STEP 4 / CHECK EACH CANDIDATE}{Repair JSON using the schema and evidence}
\textbf{Input:} one candidate JSON and a \code{checks.Doc} object containing the schema and lazily loaded text layer, reading-order text, and cached parse.\par
\textbf{Operation:} run deterministic transformations in a fixed order. Every transformation receives a fresh JSON copy. There are no model calls or answer keys.\par
\textbf{Output:} one checked candidate, still separate from every other reading.

All chains can access the same document evidence. In particular, \code{page_index} can use the cached parse in primary/parse repairs, and \code{printed_pages} can use it in any chain. A primary or one-shot candidate can therefore benefit from MinerU during checks, although its extraction call did not receive the parse. Checks never receive another candidate's JSON.

Candidate source & Exact chain\\\midrule
Primary & Repairs $\to$ Output checks\\
Parse & Spacing $\to$ Repairs $\to$ Output checks\\
One-shot / layout & Output checks only\\\bottomrule
\end{tabularx}

\sub{Spacing and repairs, in order}
\begin{tabularx}{\linewidth}{@{}p{36mm}Y@{}}\toprule
Module & Intended transformation; applies only when its guards match\\\midrule
\code{spacing} & Restore text-layer spacing when a parsed string differs only in spaces.\\
\code{carry_down} & Propagate a group value to later rows when the schema describes carry-down behavior.\\

\code{dedupe} & Deduplicate on a key identified by the list's uniqueness instructions.\\

\end{tabularx}

\sub{Output checks, in order}
\begin{tabularx}{\linewidth}{@{}p{36mm}Y@{}}\toprule
Module & Intended transformation; applies only when its guards match\\\midrule
\code{conform} & Fill nullable properties; repair missing containers and null/empty-list conventions.\\
\code{blank_boxes} & Set a blank checkbox to false when the field description requires it.\\
\code{template_rows} & Remove empty preprinted rows or template records.\\
\code{copied_rows} & Remove records spuriously copied into another array.\\
\code{record_counts} & Cap duplicate records using repetition found in document text.\\
\code{printed_pages} & Locate rows through distinctive words and correct printed page labels.\\
\code{printed_quotes} & Restore uniquely supported quote/apostrophe forms from the text layer.\\
\code{printed_numbers} & Recover uniquely supported printed precision across unit scales; integer-only fields stay unchanged.\\\bottomrule
\end{tabularx}

These are conditional heuristics. Some cannot act without suitable text evidence. \code{conform} is not a full JSON Schema validator, and a checked object is not a certificate of factual correctness. For example, missing required scalar values are not universally repaired.

\chapterpage{STEP 5 / CHOOSE A READING}{Agreement selects one complete candidate}
\textbf{Input:} checked candidates for the same document and schema.\par
\textbf{Policy:} a layout route returns its checked result; a scan longer than 12 pages returns its checked parse reading when available. Otherwise, one candidate is returned directly, several invoke the quorum, and no candidates raises an error.

\sub{The quorum calculation}
For candidate $c$, treat each other candidate $o$ as a temporary reference. The ExtractBench scorer computes value precision $P(c\mid o)$ and recall $R(c\mid o)$ under the schema. The selector explicitly supplies empty field rules and repeated-structure rules; it does not use the benchmark's annotated answer or custom matching rules.
\[
F_2(c\mid o)=\frac{5P(c\mid o)R(c\mid o)}{4P(c\mid o)+R(c\mid o)},\qquad
A(c)=\frac{1}{m-1}\sum_{o\neq c}F_2(c\mid o).
\]
If precision or recall is nonpositive, the pair contributes zero. The candidate with maximum $A(c)$ wins. Scores are rounded to nine decimals before comparison; ties go to insertion order (primary, parse, one-shot in the API).

Recall is weighted more heavily: a candidate is rewarded for retaining values found by other readers. Pairwise comparisons are directional. The selected JSON remains a complete checked candidate; fields are not voted on or stitched together.

\sub{Worked selection example}
Consider a simplified array where every item is a distinct matching value. Candidate A contains \code{[a,b]}, B contains \code{[a,b,c]}, and C contains \code{[a,b,c]}. This illustrates the arithmetic; real structured matching uses the scorer.

\begin{tabularx}{\linewidth}{@{}p{20mm}YYY@{}}\toprule
Candidate & Against first peer & Against second peer & Mean $F_2$\\\midrule
A & B: $P=1, R=2/3$ & C: $P=1, R=2/3$ & $0.714286$\\
B & A: $P=2/3, R=1$ & C: $P=1, R=1$ & $0.954545$\\
C & A: $P=2/3, R=1$ & B: $P=1, R=1$ & $0.954545$\\\bottomrule
\end{tabularx}
B wins the tie with C because B is earlier. Its complete array is returned. Agreement cannot reveal an error shared by all readings; a high agreement score is not a calibrated probability of correctness.

\sub{Step 6. Format and return}
For a JSON Schema input, return the selected object. For a template input, \code{fill_template} restores the original template shape and uses empty strings for absent leaves. The Python API returns \code{(result, report)}. A multi-candidate report includes candidate names, the pick, and rounded agreement scores. Direct returns include a readings list; the long-scan direct return reports only ``parse'', even though primary was attempted first.

\chapterpage{EXECUTION AND SCOPE}{Connect the guide to the code}\label{sec:execution}
\sub{Run a document through the API}
From the repository root, with dependencies and model endpoints configured as described in the repository README:
\begin{lstlisting}
python -m docquorum.extract invoice.pdf \
  --schema invoice_schema.json -o invoice.json
\end{lstlisting}
\begin{lstlisting}
from docquorum.extract import extract
result, report = extract("invoice.pdf", schema_dict)
\end{lstlisting}
The CLI writes the JSON to the chosen file (or stdout) and the final report to stderr. Some reader diagnostics use direct prints, so \code{-o} is the reliable way to capture a separate JSON artifact.

\sub{Benchmark runners have different orchestration}
\textbf{ExtractBench:} \code{benchmarks/extractbench/run.sh} runs primary over the split first, then parse for scans, then one-shot/quorum for short scans. Layout results overwrite general results on medium/long splits only. The script reads cached parses; prepare them with \code{python -m docquorum.tools.parser SPLIT}. Unlike the API, it does not create missing parses automatically. Its quorum command may also copy parse-only long-scan results. Scoring uses answer keys only after extraction.

\textbf{UNIKIE:} \code{benchmarks/unikie/unikie_eval.py} uses a separate template-based image protocol and six readings: image, one-shot plus parse text, one-shot, parse, and two extra-model one-shots. It uses normalized flattened-value matching for its $F_2$ quorum. It does not execute the API's layout/reader/check pipeline.

\sub{Practical limits}
Routing thresholds, row counts, and text repairs are heuristics. Parser caches can contain empty pages. Some call failures can leave partial results; the API excludes general-reader results with recorded server errors, but this does not detect every incomplete output. Specialist failures are not caught by a general-reader fallback. Inspect important extractions against the original document; neither structured decoding nor agreement proves completeness.
