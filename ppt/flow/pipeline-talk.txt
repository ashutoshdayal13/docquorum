DocQuorum: what to say for the pipeline diagram (slide "Pipeline overview")

About 10 minutes at a normal speaking pace (about 1,450 words). Words in [brackets] tell you where to point. They are not read aloud.


OPENING

This picture shows the whole DocQuorum pipeline: from the document you give it, to the
answer it gives back.

Keep two things in mind.
First, everything runs on its own. Once you give it a document, no person steps in.
Second, the model only reads. Plain Python code decides everything else: which reader to
use, what to check, and which answer to keep.

[Point at the top row]
The top row is the main path. It has six steps, from left to right.
[Point at the bottom part]
The bottom part opens up one box, the reader, and shows how it works inside.


STEP 1: INPUTS

[Point at box 1]
The user gives us up to three things.

One: the document. It can be a PDF, or a photo or scan of a page.

Two: a schema or a template. This is the list of things we want to pull out. For example:
the invoice number, the date, and every line item with its price. A schema describes each
field and its type. A template is simply an empty copy of the answer we want back.

Three, and this one is optional: a short task note in plain words. For example, "only the
wells drilled after 1950".


STEP 2: PREPARE AND ROUTE

[Point at box 2]
This step is all plain code. No model makes decisions here.

First, if the input is an image, we turn it into a PDF. After this, the pipeline only deals
with one format.

Next, we count the pages and check whether the PDF has real text inside it. Many PDFs carry
their text, so we can copy it out directly. A scanned page is only a picture. There is no
text to copy. Our rule is simple: at least 50 characters of text per page means the PDF has
text.

If there is no text, we send the pages to MinerU. MinerU is a separate model that reads
scanned pages. It gives back the text, and it gives back tables as rows and cells, so the
columns stay in place. We save this result, so it is done only once per document.

[Point at the bottom box of step 2]
Then we choose the route. We look at the page layout first. If the pages have a special
layout that our layout readers handle well, we use one of them. If not, two facts decide the
route: does the PDF have text, and how many pages does it have?


STEP 3: READ

[Point at box 3]
This is where the model reads. There are four lanes, A to D. Each document takes one lane.

[Point at lane A, orange]
Lane A is for special layouts. Some pages are printed as several equal columns of records,
like a register. Other pages are scans with a ruled table, with a line between every row.
For these we have layout readers. Code finds the columns, or the lines between rows, and
cuts the page into small pieces. The model reads one piece at a time. Because the code
counted the rows itself, we know how many rows the model should give back. We call this
answer L, for layout.

[Point at lane B, blue]
Lane B is for PDFs that have text. This is the most common case. The reader agent reads the
document once, using its text. When it reads a short document in one call, it also sees the
page images. We call this answer P, for primary.

[Point at lane C, green]
Lane C is for scans with no text, up to 12 pages. Short scans are the hardest to read, so we
read them three different ways:
  P, the reader agent looking at the page images;
  M, the reader agent reading MinerU's version of the pages;
  O, a one-shot reader that sends the whole document in a single call.
Now we have up to three separate answers for the same document.

[Point at lane D, purple]
Lane D is for scans with no text and more than 12 pages. A long scan does not fit in one
call, so there is no one-shot reading. We try the primary reading and the MinerU reading.

[Point at the circular arrow icons]
The circular arrows on P and M mean these readers adapt. They change what they do based on
what they see. I will explain this in the bottom part.


STEP 4: CHECK INDEPENDENTLY

[Point at box 4]
Every answer goes through checks before we trust it. The checks are fixed rules written in
code. No model is used here.

Each kind of answer has its own list of checks. Some examples:
  A number must be a number that is printed on the page. If the model writes 26.11 million
  but the table prints 26,107 thousand, we use the printed figure.
  If the model read the same line twice, the copy is removed.
  An empty pre-printed line on a form is not a record, so it is removed.
  If the model left a field out, we add it back as empty, so the answer always fits the
  schema.
  For the MinerU answer, we also fix spacing first. For example, scanned text often reads
  "POBOX757", and the page prints "PO BOX 757".

The important rule: a check can only fix an answer using the schema and what is printed on
the page. It never sees the correct answers of the benchmark.


STEP 5: SELECT

[Point at box 5]
Now we keep one answer. This is also plain code.

Lanes A and B give only one answer, so we keep it.

[Point at the green part, "How many?"]
Lane C can give two or three answers. If only one reading worked, we keep that one. If we
have two or three, we hold a vote. We call it the quorum.
We compare every pair of answers and measure how much they agree. Then we keep the answer
that agrees most with the others.
The idea is simple. The readers work separately. If two of them found the same values,
those values are probably right. A value only one reader made up does not get support from
the others.
We always keep one whole answer. We never stitch together pieces of different answers.

[Point at the purple part, "Parse available?"]
Lane D: if the MinerU reading worked, we keep it. If not, we keep the primary reading.


STEP 6: RETURN

[Point at box 6]
We return the extracted data as JSON, plus a short report: which readings ran, which one we
kept, and how much they agreed. If the user gave a template, we put the answer back into
the template's shape, so they get back exactly the form they asked for.


THE BOTTOM PART: INSIDE THE ADAPTIVE READER

[Point at "Inside the adaptive reader"]
This is the agent part of DocQuorum. The model does the reading, but a loop written in
Python controls it. The loop has five steps.

[Point at 1, PLAN]
Plan. Code chooses the biggest piece of work that fits in one model call. If the whole
document fits, it is read in one call. If the schema is too big, the fields are split into
groups. If the document is too long, it is read in pieces: windows of text, or a few pages
at a time for long lists of rows.

[Point at 2, ACT]
Act. The model reads that piece and fills in the schema.

[Point at 3, OBSERVE]
Observe. Code looks at the reply. Was it cut off before the end? Did the model leave out
fields? Did it return nothing for a page that clearly has five or more rows?

[Point at 4, the diamond]
If nothing is wrong, the answer goes on to the checks. This only means it passed our fixed
tests. It does not prove that every value is correct.

[Point at 5, RETRY / REPLAN]
If something is wrong, code changes the plan. It can give the model more room to write. It
can ask again and say that every field is required. It can cut the piece in half and read
each half. Or it can switch to a smaller plan.

[Point at the arrow back to PLAN]
Then it goes around again. What the code saw in one reply changes the next call.

One more point. Adaptive does not mean open-ended. Every retry rule and every limit is fixed
in code. For example, a piece is split at most four times. So the loop always ends, and the
same document always follows the same rules.


THE LEGEND AND THE NOTES AT THE BOTTOM

[Point at "How to read the automation"]
The colours tell you who does what. Grey boxes are code: routing, checks and selection. Blue
boxes are model calls: reading and parsing. The circular arrows mark the two adaptive
readers. The gear marks MinerU, which is a model, but code decides when to call it.

[Point at the line at the very bottom]
Three notes at the bottom. The picture shows the normal path, when everything works. All
readers look at the same document, but each one makes its own separate answer. And no
correct answers are used anywhere in the pipeline.


CLOSING

So, in one line: code decides, the model reads, code checks, and the readers agree on the
answer we keep.

NOTES FOR YOU (not to read aloud)

Two small differences between the picture and the code, in case someone asks:
  Box 2 says "Normalize PDF (images, rotation, etc.)". The code turns an image into a PDF.
  It does not rotate pages at this step. The ruled-table reader straightens tilted scans
  later.
  The Observe step says "emitted keys". It means fields the model left out.

Likely questions, with short answers:

Q: Why read short scans three times, but text PDFs only once?
A: With a text layer, the text itself is reliable and one reading is enough. Scans are where
   readers make different mistakes, so a vote helps. Three readings cost three times as much,
   so we spend it where it helps.

Q: Why not ask the model to check its own answer?
A: We tried about 22 different ways of doing that, and measured each one. None of them
   helped. Rules that compare the answer with the printed page did help.

Q: What if all readers agree on the same wrong value?
A: Then the vote keeps it. Agreement is not proof. The walkthrough slides show one real
   case where the vote kept a worse answer.

Q: Why does code choose the steps, instead of letting the model choose its tools?
A: It is predictable and testable. The same document always takes the same path, every
   decision is logged, and the loop always ends.

Q: Which models?
A: Open-weight models only: Qwen3.8-27B (FP8) reads, and MinerU2.5 parses scans, served on a
   single GPU.
